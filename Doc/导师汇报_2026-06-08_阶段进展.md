# 阶段进展汇报：视觉结构先验驱动的时序专家路由

汇报日期：2026-06-08

## 1. 当前研究目标

当前工作的核心目标是构建一个面向通用时序预测任务的自适应专家融合系统。系统不希望在每个新数据集上都对下游专家进行重训练，而是希望通过样本级的时序结构表示，对不同专家的适用性进行判断，并在必要时只进行轻量适配或轻量微调。

当前模型形态可以概括为：

```text
sample-channel history window
  -> pseudo-image / visual tensor
  -> visual time-series encoder
  -> visual structure embedding
  -> continuous gate / router
  -> top-k heterogeneous forecasting experts
  -> weighted forecast
```

其中，视觉模块的定位不是直接替代时序预测模型，而是学习跨窗口长度、预测 horizon 和数据源尽量稳定的时序结构先验；router/gate 是验证该结构先验是否能服务于专家选择和专家融合的下游模块。

## 2. 双路线方案

### 2.1 路线一：TimeFuse 风格的样本级专家融合

路线一偏保守，目标是先验证“样本级结构表示能否帮助多个异构专家进行连续融合”。这一条路线不强依赖 QuitoBench 的 TSF cell 分层，而是先围绕专家预测缓存和 oracle error 建立闭环。

核心流程是：

```text
输入历史窗口
  -> 提取统计特征 / 视觉伪图像 embedding
  -> 收集多个专家在同一样本上的预测结果
  -> 根据专家误差构造 soft oracle weight
  -> 训练 fusion model / continuous gate
  -> 输出专家加权预测
```

目前参考了 TimeFuse 的基本范式。TimeFuse 的优势是协议清楚：先训练多个 base forecasting models，再基于 meta-feature 学习融合权重。我们的改动点是把统计 meta-feature 扩展为“统计特征 + 视觉结构 embedding”，并比较不同 router 输入的效果。

路线一主要回答：

> 在不使用 TSF 标签监督的情况下，视觉伪图像 embedding 是否能学习到专家偏好，并缩小 fixed best expert 和 oracle ensemble 之间的 gap？

### 2.2 路线二：QuitoBench TSF 结构分层主线

路线二是更接近论文主贡献的路线。它以 QuitoBench 的官方 TSF 结构分层为主实验场景，先进行专家画像，再验证视觉结构先验在不同结构 cell、few-shot 条件、跨窗口和跨 horizon 设置下是否具有泛化性和解释性。

路线二主要回答：

> 视觉结构先验是否能在 QuitoBench 的 TSF 分层上形成可解释、可迁移的专家路由能力？

当前已经确认的 QuitoBench 基础信息包括：

- QuitoBench benchmark 包含 1,290 个 item 和 6,450 条通道序列。
- 官方 TSF cluster 来源于 Hugging Face 历史 revision 中的 `cluster` 列。
- 已反推出官方 codebook：三位三进制 digit 分别对应 `trend / seasonality / forecastability`，且 `0=high`、`2=low`。
- 通道级 full-length STL 与官方 codebook 的 item exact match 为 68.37%，T/S/F 逐维匹配分别为 81.32% / 69.30% / 100.00%。

因此，后续路线二中会把官方 TSF cell 作为分层报告标签，而不是直接把它当作 sample-level router 的硬监督。router 的主要监督仍来自同一 sample-channel/horizon 下各专家的预测误差和 soft oracle。

## 3. 已完成工作

### 3.1 QuitoBench 数据与标签审计

已完成 QuitoBench 数据充分性审计、官方 TSF cluster 定位、codebook 反推和通道级 STL 验证。当前结论是：QuitoBench 的规模和结构分布可以支撑第一阶段实验，但官方构造口径和本地 STL 复现口径并不完全一致，因此不能简单用本地 STL 标签替代官方 cell。

### 3.2 窗口 registry 与样本级协议

已建立 QuitoBench sample-channel 窗口索引与配置注册表，并对齐 Quito 的切窗口径。当前 working registry 采用 `quito_overlap + sample_stride=96`，包含约 62.7 万条窗口。

同时已经稳定了三层 ID schema：

- `physical_window_id`
- `base_registry_id`
- `sample_set_id`

这一步为后续专家预测缓存、视觉 embedding 缓存和 router 训练提供了统一索引。

### 3.3 轻量 proxy 与视觉伪图像协议

已完成 sample-channel light proxy 的预计算和在线 torch kernel。每个窗口包含 15 个 history-only proxy 特征，特征可用于后续与视觉 embedding 组合。

已完成三视图 `view_tensor` 伪图像协议 smoke test，当前视觉输入形态为：

```text
[B, 3, 64, 192]
```

并已验证这些 view tensor 可以被 visual embedding cache smoke 消费，生成与 `physical_window_id` 对齐的视觉 embedding。

### 3.4 专家预测缓存初步建设

已建立轻量专家 prediction/error/oracle 缓存协议，并完成 seasonal naive 全量 baseline。也已接入 DLinear、PatchTST、TSMixer 等训练型专家的 smoke 和分层抽样实验。

目前已经具备后续训练 router 所需的基本缓存结构：

```text
(physical_window_id, expert_id)
  -> prediction
  -> error
  -> soft oracle weight
```

## 4. 当前主要问题与阻塞

### 4.1 QuitoBench 实际数据集抽取仍然复杂

QuitoBench 的官方任务口径、benchmark parquet、历史 revision 中的 cluster 标签、Quito 原生 `TimeSeriesDataset` 切分逻辑、scaler 逻辑之间存在多层适配关系。虽然目前已经可以构建 registry 和稀疏样本，但如果要严格复现官方表格，还需要进一步确认：

- full-window 还是 sparse-window 的评估口径；
- `features=S` 下多通道拆分为单变量样本的具体行为；
- seasonal naive 的 period 设置；
- Quito dataset scaler 的训练段复用方式；
- 官方 trainer / checkpoint / evaluation script 的完整流程。

这导致“实际数据集抽取”不是简单下载 parquet 后切窗口，而是需要对齐官方数据加载、归一化、窗口枚举和评估协议。

### 4.2 复现结果与常识预期存在明显差距

在前期 sparse sanity 中，出现过 PatchTST、DLinear 和 seasonal naive 排序异常的问题，表现为复杂神经模型明显弱于简单 seasonal naive，或者不同指标下排序不稳定。这与常识预期和论文中常见结果存在差距。

后续排查发现，部分异常与以下因素有关：

- seasonal period 口径不一致；
- normalize / scaler 口径不一致；
- 模型窗口长度没有完全跟随 registry；
- PatchTST 的 RevIN、学习率、训练预算和输出尺度适配存在不稳定；
- 稀疏抽样 sanity 与官方 full-window 评估并不等价。

在最近一次官方关键口径对齐后，DLinear 相对 SNaive 的排序已有改善，PatchTST 在 MSE 上也不再完全失真，但整体仍未形成可直接声称“复现官方结果”的完整闭环。

因此，目前阻塞点不是单个模型没有跑通，而是：

> 还没有推出 Quito 官方完整训练、预测、评估全流程，因此不能贸然固化专家池，也不能直接进入 train 上训练 router、记录 train/vali/test 预测缓存并训练最终 gate。

如果在这个阶段继续向下游推进，router 很可能学习到的是错误专家缓存或不稳定口径下的专家偏好，影响后续结论可信度。

### 4.3 TimeFuse 可参考，但数据集选择与研究目标并不完全一致

TimeFuse 目前正在尝试使用。它的流程对我们很有价值，但它默认会回到常见 LTSF 数据集，例如 ETT、Electricity、Traffic、Weather。

这些数据集有两个问题：

1. 它们在社区里使用广泛，但本身可能存在偏置。例如 ETT 周期性较强，Weather 存在异常值和分布问题。
2. 它们更适合做传统 benchmark 对比，不完全对应我们想构建的“新数据/新数据集到来时，尽量不重训下游专家，只做合理适配或轻量微调”的通用系统目标。

因此，TimeFuse 更适合作为融合协议和 sanity check，而不应成为唯一实验场景。更合理的定位是：

- 用 TimeFuse 验证样本级融合协议是否工作；
- 用常见数据集做外部 sanity check；
- 主要结论仍然放在 QuitoBench 及其结构分层上；
- 后续强调跨数据源、跨 horizon、跨 window 的轻量适配能力。

## 5. 当前阶段的判断

目前已经完成了底层数据协议、窗口索引、轻量特征、伪图像协议、视觉 embedding smoke、专家缓存 schema 和若干专家接入实验。换言之，工程链路的下半部分已经具备雏形。

但现在不适合马上进入最终 router 训练，原因是专家侧的可复现性还没有完全稳定。router 的训练质量高度依赖专家预测缓存，如果专家缓存本身来自未对齐官方口径的训练和评估流程，那么后续融合结果即使提升，也很难解释。

当前最重要的工作应从“继续堆 router 模块”转为“先把专家池和官方口径对齐稳定下来”。

## 6. 下一步计划

### 6.1 优先推出 Quito 官方近似全流程

下一步优先围绕 Quito 官方流程做最小闭环：

1. 固化数据抽取、scaler、window registry 和评估口径。
2. 在 `96_48_S` 和 `576_288_S` 两个关键设置上先做小规模但口径完整的 sanity。
3. 尽量复用官方 trainer / evaluation 逻辑，减少自写 wrapper 引入的偏差。
4. 明确 sparse sanity、full-window evaluation 和论文表格之间的差异。

### 6.2 稳定专家池

专家池暂时不宜继续盲目扩大。建议先稳定以下几类：

- seasonal naive：保留为强统计 baseline；
- DLinear：作为稳定、可解释的线性分解专家；
- PatchTST：保留但需要继续做官方口径和训练稳定性适配；
- 频域或多尺度统计专家：用于补充和 seasonal naive / DLinear 的互补性。

只有当专家在统一口径下形成可解释的互补性后，再生成 train/vali/test 的预测缓存。

### 6.3 再进入 router 和视觉结构先验验证

当专家缓存稳定后，再进入：

1. 构造 per-window expert error matrix；
2. 生成 best expert id 和 soft oracle weight；
3. 训练 statistical router、visual router、visual + proxy router；
4. 比较 fixed best、average ensemble、oracle ensemble 和 learned gate；
5. 按 QuitoBench 官方 TSF cell 做分层分析；
6. 做跨 window/horizon 和 few-shot 适配实验。

### 6.4 TimeFuse 的使用方式

TimeFuse 后续作为两类用途：

- 协议参考：复用其 meta-feature、fusion model、weighted fusion 评估思想；
- 外部 sanity：在 ETT / Weather 等常见数据集上验证我们的 router 实现没有工程问题。

但主线结论仍应尽量回到 QuitoBench，因为它更贴近我们关于结构先验、专家适配和通用系统的研究问题。

## 7. 希望和导师讨论的问题

1. 当前是否认可“双路线并行”的定位：路线一做融合协议验证，路线二做 QuitoBench 结构分层主线？
2. 在官方复现尚未完全稳定前，是否应暂停最终 router 训练，优先补齐 Quito 官方全流程？
3. TimeFuse 是否只作为协议参考和外部 sanity，而不作为主实验数据来源？
4. 专家池是否应先收缩为少量稳定且互补的专家，而不是继续扩充模型数量？
5. 后续论文叙事是否应强调“通用结构先验 + 轻量适配”，而不是在固定 benchmark 上追求单一预测模型 SOTA？

## 8. 汇报总结

当前工作已经从数据审计推进到样本窗口协议、视觉输入协议和专家缓存协议，整体工程链路正在成型。主要瓶颈集中在 QuitoBench 官方数据抽取与专家复现口径对齐上。由于 router 的监督依赖专家误差，如果专家侧尚未稳定，过早训练 router 会削弱后续结论的可信度。

因此，下一阶段建议优先完成 Quito 官方近似全流程复现和专家池稳定，再进入视觉 router 训练与 TSF 分层分析。TimeFuse 可以作为融合协议和外部 sanity check，但主线仍应服务于“面向新数据集的通用时序结构先验与轻量专家适配”这一研究目标。
