# 双路线并行任务拆解与路线 1 实施计划

## 0. 当前决策

当前先放弃合成数据分支，不再引入 `Gratis`。本阶段只围绕两类真实数据来源展开：

- Quito 提供的预训练数据集。
- QuitoBench benchmark 数据。

实现上不直接改 `quito` 主代码，而是在根目录新建一个独立实验包：

```text
vision_ts_routing/
```

这个包负责视觉伪图像、专家预测缓存、oracle 路由标签、router 训练、评估指标和两条路线的实验入口。`quito` 作为数据、模型和评估能力的参考与适配对象。

核心原则：

1. 先做两条路线共享的模块。
2. 视觉模块的核心目标不是拟合某一个窗口设置下的专家 oracle label，而是学习跨 `history_len`、`pred_len`、subset/data source 都尽量稳定的时序结构先验。
3. 路线 1 先跑通 TimeFuse 风格的样本级异构专家连续融合，用来验证视觉先验是否能迁移到专家偏好任务。
4. 路线 2 后续复用共享模块，进入 QuitoBench TSF cell 分层、few-shot 和跨结构泛化实验。
5. router 是视觉先验的下游验证器，不应把视觉模块本身定义成单一窗口设置下的分类器。
6. 第一版优先使用冻结专家或已训练专家的预测缓存训练 gate，不做异构专家端到端联合训练。
7. 两条路线分目录推进，但不要做成两套割裂系统。
8. 正式评估优先使用 QuitoBench；预训练数据集只作为后续视觉编码器预训练或扩大无监督样本的扩展资源。

### 0.0 研究目标校准：全局视觉时序结构先验

当前课题的主目标应表述为：

> 通过通道独立的伪图像/视觉张量表示，学习 sample-channel 历史窗口中的时序结构先验，并验证该先验能否跨窗口长度、预测 horizon 和数据源迁移到异构时序专家的连续自适应融合任务。

因此，后续实验需要区分四类对象：

| 对象 | 粒度 | 角色 |
| --- | --- | --- |
| official cluster / TSF cell | item 级、多变量、全长 | 结构解释与分层报告标签，不作为 sample-level router 的硬监督 |
| channel full-length STL | item-channel 级、全长 | 分析通道异质性，辅助解释官方 TSF cell |
| sample-channel window | 单样本、单通道、历史窗口 | 视觉模块和 router 的实际输入单位 |
| expert oracle / soft weights | sample-channel + horizon | 下游 router 训练目标 |

推荐的最终模型形态是：

```text
sample-channel history window
  -> pseudo-image / visual tensor
  -> visual time-series encoder
  -> visual structure embedding
  -> continuous gate
  -> top-k heterogeneous forecasting experts
  -> weighted forecast
```

其中 continuous gate 可以同时接收：

- visual embedding；
- 轻量 sample-channel proxy/meta-features；
- `history_len`、`pred_len`、period、subset 等配置 embedding；
- normalization/scale metadata。

第一版推理建议采用 `top-k soft routing`：训练时可用完整专家预测缓存学习 soft oracle，在线推理时只调用 gate 选出的少量专家，避免 dense ensemble 调用全部专家。

### 0.1 Quito 两类数据的角色

需要明确区分：

| 数据来源 | 角色 | 当前阶段是否使用 |
| --- | --- | --- |
| Quito 预训练数据集 / corpus | 大规模无监督或弱监督预训练资源 | 暂不作为路线 1 主实验；后续可用于视觉编码器预训练 |
| QuitoBench benchmark | 正式预测评估、专家画像、TSF cell 分层、few-shot 实验 | 当前主数据 |

路线 1 和路线 2 的第一阶段都应围绕 QuitoBench，而不是预训练数据集。

预训练数据集的可能用途是：

- 预训练视觉伪图像 encoder。
- 学习通用 TSF 结构 embedding。
- 增强 `L_tsf` 或自监督重建任务。

但它不适合作为第一阶段主结论来源，因为我们的核心结论需要标准 benchmark、专家评估和可复现切分。

### 0.2 Stage 0 已完成结论与当前约束

截至 Stage 0.7，已经确认：

- QuitoBench benchmark 包含 1,290 个 item 和 6,450 条通道序列，窗口数量足以支撑第一阶段实验。
- 官方 TSF cluster 来自 Hugging Face 历史 revision `17362dcb` 的 `cluster` 列。
- Stage 0.6b 已确认官方 codebook：三位三进制 digit 依次为 `trend / seasonality / forecastability`，digit `0=high`、`2=low`。
- Stage 0.7 已完成通道级 full-length STL 验证：channel-mean + `tau=0.4` 与官方 codebook 的 item exact match 为 68.37%，T/S/F 逐维匹配为 81.32% / 69.30% / 100.00%。
- Stage 0.7 中 cluster 24 与官方 `lowT_lowS_highF` 100% 匹配，说明 Stage 0.6 的 cluster 24 冲突主要来自 item 代表序列口径。
- 本地 full-length STL 仍不能完全复现官方 regime 构造，尤其 cluster 6、8、26 在 trend/seasonality 上存在差异。

因此后续实验中：

- Stage 0.6b 官方 codebook 作为路线 2 的官方解释标签。
- Stage 0.7 通道级 STL 作为通道异质性分析和伪图像设计参考。
- 不把 official cluster 或 STL cell 直接当作 sample-channel router 的硬标签。
- router 的主要监督来自同一 sample-channel/horizon 下的异构专家预测误差和 soft oracle。

## 1. TimeFuse 调研结论

### 1.1 TimeFuse 的核心思想

TimeFuse 是一个样本级自适应模型融合框架。它不直接提出一个新的预测专家，而是：

1. 训练多个 base forecasting models。
2. 对每个输入窗口提取 meta-features。
3. 收集每个专家对同一个样本的预测结果。
4. 用 meta-features 训练 fusion model。
5. fusion model 输出专家融合权重。
6. 对多个专家预测做 weighted sum。

这和我们的路线 1 很接近。区别是：

- TimeFuse 用统计 meta-features。
- 我们要加入视觉伪图像 embedding。
- 我们要比较统计 router、视觉 router、视觉 + 统计 router。
- 后续路线 2 还要把视觉 router 放进 QuitoBench TSF 结构分层里解释。

### 1.2 TimeFuse 的代码结构可借鉴点

TimeFuse 仓库：<https://github.com/ZhiningLiu1998/TimeFuse>

可借鉴的模块思想：

- `meta_feature.py`
  - 统计特征提取。
  - 包括均值、方差、偏度、峰度、ACF、ADF、变化率、自回归系数、频域峰值、谱熵、协方差统计等。

- `timefuse.py`
  - meta dataset 的组织方式。
  - `x_meta`
  - `y_model_preds`
  - `y_true`
  - `ModelFusor`
  - weighted fusion 评估流程。

- `run_config.json`
  - 默认数据集是 `ETTh1`、`ETTh2`。
  - 默认模型包括 `DLinear`、`PatchTST`、`TimesNet`、`PAttn`、`TimeMixer`、`TimeXer`。
  - 默认预测设置是 `[96, 48, 96]`，即 `seq_len=96`、`label_len=48`、`pred_len=96`。

### 1.3 TimeFuse 使用的数据集

从 TimeFuse 脚本目录看，它主要覆盖：

| 脚本目录 | 数据集 | 数据文件/路径形式 |
| --- | --- | --- |
| `ETT_script` | `ETTh1`、`ETTh2`、`ETTm1`、`ETTm2` | `dataset/ETT-small/*.csv` |
| `ECL_script` | Electricity / ECL | `dataset/electricity/electricity.csv` |
| `Traffic_script` | Traffic | `dataset/traffic/traffic.csv` |
| `Weather_script` | Weather | `dataset/weather/weather.csv` |

TimeFuse 的数据加载器还支持：

- `ETTh1`
- `ETTh2`
- `ETTm1`
- `ETTm2`
- `custom`
- `PEMS`

其中 Electricity、Traffic、Weather 都走 `custom` 数据集接口。

### 1.4 对我们的路线 1 的启发

路线 1 不一定要使用 TimeFuse 的数据设置。TimeFuse 更适合作为融合协议参考，而不是数据集约束。它给我们的核心启发是：

```text
输入窗口特征
-> 多专家预测缓存
-> 样本级融合权重
-> weighted sum
-> 和单专家/平均融合/全局权重对比
```

如果 QuitoBench 的数据规模和 cell 分布足够，路线 1 可以直接使用 QuitoBench。TimeFuse 数据集只保留为外部泛化检查。

因此当前更合理的顺序是：

1. 先复现 TimeFuse 风格的数据协议和融合任务。
2. 优先审计 QuitoBench 是否足够支撑路线 1 和路线 2。
3. 如果 QuitoBench 足够，路线 1 直接从 QuitoBench 普通切分开始。
4. 如果需要外部 sanity check，再使用 TimeFuse 默认设置：
   - `ETTh1`
   - `ETTh2`
   - `seq_len=96`
   - `label_len=48`
   - `pred_len=96`
5. 后续可扩展到：
   - `ETTm1`
   - `ETTm2`
   - Electricity
   - Weather
   - Traffic

这样路线 1 可以回答：

> 在不使用 TSF 标签监督的情况下，视觉伪图像 embedding 能否学习专家偏好？

路线 2 再回答：

> 在 QuitoBench TSF 结构分层和 few-shot 条件下，视觉结构先验是否有更强解释性和泛化性？

## 2. QuitoBench 是否足够：规模比较与审计计划

### 2.1 初步规模比较

从公开资料看，TimeFuse 使用的传统 LTSF 数据集主要是 ETT、ECL、Traffic、Weather。常见统计如下：

| 数据集 | 时间步 | 变量数 | 粗略 value cell 数 |
| --- | ---: | ---: | ---: |
| `ETTh1` | 17,420 | 7 | 121,940 |
| `ETTh2` | 17,420 | 7 | 121,940 |
| `ETTm1` | 69,680 | 7 | 487,760 |
| `ETTm2` | 69,680 | 7 | 487,760 |
| Electricity / ECL | 26,304 | 321 | 8,443,584 |
| Traffic | 17,544 | 862 | 15,122,928 |
| Weather | 52,696 | 21 | 1,106,616 |

这些数据集合计约：

```text
252,858 个时间步口径
约 24.9M 个 value cell 口径
```

QuitoBench 公开 Hugging Face 数据集有两个 subset：

| subset | 公开 rows |
| --- | ---: |
| `hour` | 约 7.94M |
| `min` | 约 4.56M |
| 合计 | 约 12.5M |

注意：这两个口径不完全等价。

- TimeFuse 传统数据集通常是“单个多变量矩阵”：`time steps x variables`。
- QuitoBench 是 CloudOps 多 item 的 parquet 数据，公开 rows 更接近“item-time 记录”口径。
- 如果每条记录还包含多个指标列，QuitoBench 的有效 value cell 数会高于 rows。

因此不能只用一个数字做结论。真正关键的是：

> QuitoBench 是否有足够多的 item、窗口和 TSF cell 样本。

### 2.2 初步判断

只用 QuitoBench 大概率是可行的，原因是：

1. 公开 benchmark 已是千万 row 级。
2. 数据来自大量 CloudOps item，比 ETT 这类单站点数据更适合学习样本级专家偏好。
3. QuitoBench 有 forecastability、seasonality、trend 等质量分析工具，天然适合做 cell-level reporting。
4. 路线 1 和路线 2 可以共用同一批专家预测缓存，实验资产复用更高。

但在正式决定“只用 QuitoBench”之前，需要完成一次数据充分性审计。

### 2.3 数据充分性审计内容

审计对象：

```text
QuitoBench hour
QuitoBench min
```

审计指标：

1. `hour` / `min` 各有多少 `item_id`。
2. 每个 `item_id` 的有效长度分布。
3. 在不同窗口设置下能切出多少样本：
   - `seq_len=96, pred_len=96`
   - `seq_len=192, pred_len=96`
   - `seq_len=336, pred_len=96`
4. trend strength 分布。
5. seasonality strength 分布。
6. forecastability 分布。
7. 8 个 TSF cell 的样本数。
8. 每个 cell 中 train/valid/test 是否都足够。
9. 每个 cell 是否支撑 few-shot 设置：
   - 1-shot
   - 5-shot
   - 10-shot
   - 50-shot
10. 每个 cell 中不同专家是否存在明显性能差异。

### 2.4 决策门槛

如果满足下面条件，就可以第一阶段只用 QuitoBench：

1. 至少 6 个 TSF cell 有足够样本。
2. 每个主要 cell 至少有数千个可用窗口。
3. 每个主要 cell 都能划分 train/valid/test。
4. 专家之间存在可测的 oracle gap。
5. `hour` 或 `min` 至少一个 subset 能稳定支撑专家 profiling。

如果 8 个 cell 明显不均衡，也不一定放弃 QuitoBench，可以改成：

- 用 quantile threshold 重新划分 high/low。
- 合并极少数 cell。
- route 1 使用 QuitoBench 全量普通切分。
- route 2 只在样本充足的 cell 上做主实验，稀疏 cell 作为补充分析。

### 2.5 当前建议

当前建议是：

> 先默认只使用 QuitoBench，但把“数据充分性审计”作为第一个实验任务。

如果审计结果显示 QuitoBench 的 cell 分布和窗口数量都足够，那么 TimeFuse 数据集不进入第一阶段，只作为后续外部泛化检查。

### 2.6 Quito 封装对我们的帮助

Quito 的封装对实验很有帮助，但需要分清“可以直接复用”和“需要扩展”的部分。

可以直接复用：

1. **数据加载与切窗**
   - `quito.datasets.TimeSeriesDataset` 已经支持 parquet、`item_id`、train/valid/test、`S/M` 特征模式。
   - `__len__` 中已经按照 `seq_len` 和 `forecast_horizon` 计算滑动窗口数量。

2. **模型专家池**
   - Quito 已经封装了 DLinear、PatchTST、TSMixer、iTransformer、Crossformer、snaive、ES、Chronos、TimesFM、TiRex 等。
   - 这可以减少我们重写专家模型的工作量。

3. **配置化训练/微调/评估**
   - `quito-cli pretrain`
   - `quito-cli finetune`
   - `quito-cli evaluate`
   - 对应配置在 `configs/pretrain/`、`configs/finetune/`、`configs/evaluate/`。

4. **数据质量工具**
   - `forecastability`
   - `seasonality strength`
   - `trend strength`
   - missing ratio
   - effective length
   - 这些可以直接用于 TSF cell 构造。

5. **按 item 聚合评估**
   - `examples/data_analysis/aggregate_results.py` 可以把不同模型的评估结果按 `item_id` 聚合。
   - 这对专家 profiling 有帮助。

需要扩展：

1. **逐窗口专家预测缓存**
   - Quito 的 `evaluate.py` 主要输出按 user/item 聚合后的 metrics。
   - 我们的 router 需要每个窗口的：

```text
X_window
y_true
y_pred_model_1
y_pred_model_2
...
expert_errors
```

   因此需要在 Quito eval loop 或模型 wrapper 旁边加一个缓存导出层。

2. **样本级 oracle target**
   - Quito 原生评估不直接生成 `N x K` 的专家误差矩阵。
   - 我们需要把多个专家在同一批窗口上的预测对齐，再生成 soft oracle。

3. **视觉伪图像路径**
   - Quito 专家模型直接吃时间序列。
   - 我们需要额外从同一个 `X_window` 生成伪图像，供视觉 encoder/router 使用。

结论：

> Quito 的数据、专家、配置、质量分析和评估框架都应尽量复用；但 sample-level visual router 需要新增“逐窗口预测缓存 + oracle target + 伪图像 embedding”这一层。

### 3.1 `shared/` 职责

两条路线共同使用。

- `imageization.py`
  - GPU 端伪图像构造。
  - 输入统一为 `B x L x C`。
  - 输出统一为 `B x C_img x H x W`。

- `routing_targets.py`
  - 根据专家误差生成 hard oracle 和 soft oracle。

- `routing_metrics.py`
  - 计算 oracle gap、routing entropy、expert utilization entropy、top-k oracle coverage。

- `experiment_records.py`
  - 定义专家预测、专家误差、router 输出、评估结果的数据结构。

- `prediction_cache.py`
  - 统一保存和加载 `y_true`、`y_model_preds`、`expert_errors`。

### 3.2 `route1_generic/` 职责

路线 1 使用。

目标是复刻 TimeFuse 的融合设置，并加入视觉 router。

主要比较：

- best fixed expert
- uniform ensemble
- global weighted ensemble
- TimeFuse-style statistical router
- visual router
- visual + statistical router

### 3.3 `route2_quito/` 职责

路线 2 使用。

目标是把路线 1 的“视觉伪图像 embedding 能否学习专家偏好”进一步解释为：

> 视觉结构先验在哪些 TSF 结构上有效，是否能在 few-shot 条件下快速适配新的结构 regime？

路线 2 不重新实现共享模块，而是复用路线 1 和 `shared/` 的产物：

- 逐窗口专家预测缓存。
- `expert_errors: N x K`。
- hard/soft oracle routing target。
- 视觉伪图像模块。
- visual/statistical router baseline。
- oracle gap、routing entropy 等指标。

路线 2 分成四个阶段：

#### 2A：数据分层与专家画像

目标：

> 证明 QuitoBench 不同 TSF cell 中存在专家偏好和互补性。

输出：

- TSF cell 标签构造。
- cell-level expert profiling。
- `cell x model` 性能矩阵。
- oracle ensemble upper bound。
- 专家池筛选依据。

#### 2B：TSF 监督视觉编码

目标：

> 让视觉编码器显式学习 trend、seasonality、forecastability 和 8-cell regime。

输出：

- TSF 标签预测结果。
- visual embedding 与 TSF 标签的一致性分析。
- `L_tsf`、`L_route`、`L_tsf + L_route` 消融。

#### 2C：few-shot router adaptation

目标：

> 在每个 TSF cell 内只给少量样本，验证视觉 router 是否能快速校准专家权重。

输出：

- few-shot split。
- few-shot router adaptation。
- 1/5/10/50-shot 结果。
- 和统计 router、hard TSF router、固定 ensemble 的对比。

#### 2D：leave-one-cell-out 泛化

目标：

> 检验视觉结构先验是否能迁移到训练时未见过的 TSF cell。

输出：

- 8 轮 leave-one-cell-out 结果。
- held-out cell 的 oracle gap。
- routing-regime agreement。
- 失败 cell 分析。

## 4. 任务拆解

### Task 0：QuitoBench 数据充分性审计

目标：

> 在正式实现路线 1 之前，确认只使用 QuitoBench 是否足够。

审计对象：

```text
QuitoBench hour
QuitoBench min
```

需要统计：

- `hour` / `min` 各有多少 `item_id`。
- 每个 `item_id` 的有效长度分布。

| subset | item_id | channel | start_idx | history_len | pred_len | period | official_cluster | official_tsf_cell | split | window_id |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | --- | --- | --- |
| hour | item_0007 | ind_1 | 1000 | 192 | 96 | 24 | 24 | lowT_lowS_highF | train | abc123 |

建议输出：

```text

outputs/vision_ts_routing/window_registry/<config_hash>/config.yml
outputs/vision_ts_routing/window_registry/<config_hash>/manifest.json
```

其中需要区分三类 ID，避免后续 changing sample policy 造成缓存返工：

| ID | 含义 | 是否受采样策略影响 | 用途 |
| --- | --- | --- | --- |
| `physical_window_id` | 单个真实 sample-channel 窗口身份：dataset/revision/subset/item/channel/split/target_start/history_len/pred_len | 否 | proxy、伪图像、专家预测缓存的主键 |
| `base_registry_id` | 合法窗口母体定义：Quito split、history/pred、overlap policy | 否 | 说明窗口来自哪个母体 |
| `sample_set_id` | 具体取样集合：如 stride96、stratified_v1、smoke | 是 | 训练/验证/测试实验入口和输出目录 |

`config_hash` 仅保留为兼容字段；后续新缓存应优先使用 `physical_window_id` 和 `sample_set_id`。

Stage 1.0 已做口径和 schema 修正：默认窗口生成应复用 Quito `TimeSeriesDataset` 的样本构造方式，而不是旧版 strict split 内大步长口径。官方兼容 working 配置建议为：

```text
history_len=192
pred_len=96
sample_stride=96
split_strategy=quito_temporal
split_context_policy=quito_overlap
```

`quito_overlap` 的含义是 valid/test 的 target 必须落在当前 split 内，但 history 允许向前借用 `history_len` 个上下文点；train 没有前置上下文。`sample_stride=96` 不是分层采样，而是第一版规则降采样 working set，规模约 62.7 万 sample-channel；旧版 `strict_within_split + sample_stride=96` 只能作为 coarse 对照，不再当作 Quito 兼容口径。按 `history_len=192,pred_len=96,sample_stride=1` 估算，QuitoBench 全量 sample-channel 窗口约 5,943.8 万条，不建议直接写单个 CSV；后续如需结构均衡，可新增 stratified `sample_set_id`，但不得改变已有 `physical_window_id`。

  - best fixed expert
  - uniform ensemble
  - global weighted ensemble
  - statistical router
  - visual router
  - visual + statistical router
- 输出 MSE、MAE、oracle gap、routing entropy、expert utilization entropy。
